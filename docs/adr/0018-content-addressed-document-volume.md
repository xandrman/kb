# ADR-0018: Хранилище исходных документов — Docker volume с адресацией по sha256

Статус: принят  
Deciders: AI Architect  
Дата: 2026-09-22  
Техническая история: ТЗ-ТМ-2026-014, п. 2.2, 3.1 (поз. 3), 4.1, 4.2, 4.3, 4.4, 5 (FR-1, FR-2, FR-5, FR-7), 6.2, 6.3, 6.4, 6.5, 7.5, 7.6, 8.3

## Контекст

П. 7.5 перечисляет четыре хранилища: векторное (ADR-0006), графовое (ADR-0007), реляционное (ADR-0014), кэш/очереди (Redis, введён ADR-0012 под FR-1). Место для самих файлов в п. 7.5 не названо, но требуется тремя пунктами: загрузка документов через админ-панель и **повторная обработка** (FR-1, 3.1 поз. 3), подача файла в извлечение (FR-2), ссылки на источники (FR-5).

ADR-0012 выбрал docling-serve и описал маршрутизацию, но не сказал, откуда воркер берёт файл и что происходит с оригиналом после извлечения. В `infra/main.tf` (ADR-0001) у контейнера `kb-docling` нет ни одного тома — долг зафиксирован в коде.

Масштаб: 125–500 документов до 50 страниц (4.3), PDF и растровые сканы — единицы-десятки гигабайт на корпус. Контур air-gapped, self-hosted (6.3); сегментация DMZ/Internal, аудит доступа к ограниченным документам (6.4); сопровождение после сдачи принимает PHP-команда без DevOps (2.2).

## Драйверы

- **Повторная обработка (FR-1) невозможна без оригинала.** Тот же оригинал нужен при смене embedding-модели (ADR-0010), стратегии чанкования или порогов гейта маршрутизации (ADR-0012): переиндексация корпуса не должна требовать повторной загрузки файлов пользователем.
- **Идемпотентность ingest против бюджета 6.2.** Документ до 100 страниц — до 30 минут, и на VLM-маршруте это GPU-время, конкурирующее с чатом. Повторная загрузка того же файла обязана отсекаться **до** запуска конвейера. Хэш содержимого даёт это без отдельного механизма дедупликации.
- **Владелец грифа — PostgreSQL (ADR-0014), и путь к файлу не должен быть его пятой копией.** Раскладка по хэшу структурно не способна нести SKU, отдел или гриф (4.2): в пути нет ничего, кроме содержимого. Именующая раскладка (`/конфиденциальные/<отдел>/…`) потребовала бы транзакционного переименования при смене грифа — операции, которой у файловой системы нет.
- **Неизменяемость делает переиндексацию воспроизводимой.** Адрес, равный хэшу, исключает изменение файла на месте: «новая версия документа» — это новый объект, а не перезапись. Расследование расхождений (8.3) опирается на то, что вход конвейера не менялся задним числом.
- **Объектное хранилище на этом масштабе не окупается.** MinIO — пятый stateful-контейнер со своими учётными данными, политиками и порядком бэкапа при корпусе в десятки гигабайт на одном узле. П. 6.5 требует горизонтального масштабирования Data Plane, а не хранилища файлов пилотного корпуса.
- **Повторный парсинг стоит дороже хранения его результата.** Результат извлечения на VLM-маршруте недетерминирован (сэмплинг), поэтому «перечанковать» документ, не сохранив разобранное представление, означает второй прогон VLM с другим результатом. Markdown для этого непригоден — при экспорте теряется провенанс страниц, необходимый FR-3/FR-5.

## Варианты

| | Суть |
|---|---|
| **A. Docker volume, адресация по sha256** | Ноль новых контейнеров; дедупликация и идемпотентность из адресации; неизменяемость по построению; версионирование и lifecycle отсутствуют — переносятся в реестр и код |
| B. MinIO (S3 API) | Versioning, lifecycle, object lock, событийные нотификации из коробки; шов на будущий второй узел; цена — пятый stateful-контейнер и второй контур учётных данных при 2.2 |
| C. `bytea` / Large Object в PostgreSQL | Одна транзакция на файл и метаданные, RLS распространяется на содержимое; цена — WAL и `pg_dump` пухнут на порядок от сканов, toast-таблицы вместо потоковой отдачи |
| D. Не хранить оригинал, только извлечённый текст | Минус хранилище — минус FR-1 (повторная обработка), минус переиндексация при смене модели, минус показ первоисточника |

## Решение

**Вариант A.**

Том `kb-documents` (`docker_volume` в `infra/main.tf`) монтируется **только в контейнеры PHP-слоя** (7.6): загрузчик админ-панели — `rw`, воркер и слой выдачи — `read_only`. В `kb-docling` том не пробрасывается: по ADR-0012 взаимодействие с ним идёт только по HTTP, файл уходит телом запроса.

### Раскладка

```
/data/documents/
  raw/<xx>/<sha256>              # оригинал как принят, без расширения
  extracted/<xx>/<sha256>.json   # DoclingDocument, результат ADR-0012
```

`<xx>` — первые два hex-символа дайджеста. Расширения нет: MIME-тип живёт в реестре, а одно содержимое не должно быть доступно под двумя именами.

### Запись

Публикация файла в `raw/` атомарна: под целевым путём оказывается либо полностью записанное содержимое, либо ничего. Если целевой путь уже существует — это дубликат: запись отменяется, конвейер не запускается, в реестре появляется вторая запись документа, ссылающаяся на тот же blob.

### Реестр и связи

Единственный владелец метаданных — PostgreSQL (ADR-0014): дайджест, MIME-тип, имя при загрузке, гриф (4.2), статус обработки (FR-1), маршрут ADR-0012, версия конвейера, счётчик ссылок на blob. Цепочка версий документа — там же; файловая система связи версий не выражает.

### Доступ

Том не раздаётся Nginx как статика ни при каких условиях. Отдача файла — через контроллер PHP, выполняющий запрос к метаданным под RLS (ADR-0014) до открытия файла. Путь, состоящий из хэша, неугадываем, но неугадываемость контролем доступа не является.

### Удаление

Изъятие ПДн (4.4) и удаление документа — единственная операция, нарушающая неизменяемость. Порядок: снятие записи реестра, декремент счётчика ссылок, физическое удаление blob только при нуле; запись в аудит-лог (6.4). Автоматической сборки осиротевших blob нет — sweep запускается оператором и сверяется с реестром.

### Проверка целостности

Дайджест пересчитывается при каждом чтении для повторной обработки и сверяется с путём. Том лежит на одном диске без репликации — это единственная защита от порчи файла.

### Шов расширения (6.5)

Доступ к blob инкапсулируется в один интерфейс PHP-слоя с операциями `put(bytes): Digest`, `get(Digest): Stream`, `exists(Digest): bool`, `delete(Digest): void`. Ключ, равный хэшу, переносится в ключ объекта S3 один в один, поэтому замена реализации на MinIO не затрагивает ни схему PostgreSQL, ни конвейер.

## Последствия

Плюс: ни одного нового контейнера при закрытии пункта 7.5 целиком; дедупликация, идемпотентность и проверка целостности получены из одного механизма адресации; оригиналы неизменяемы, поэтому переиндексация при смене модели воспроизводима; гриф доступа не появляется в путях и остаётся в единственном владении PostgreSQL; сохранённый DoclingDocument позволяет менять чанкование без повторного прогона VLM; переход на MinIO — замена одной реализации интерфейса.

Минус: **том привязан к узлу** — при появлении второго узла Data Plane (6.5) воркеры на нём файлов не увидят; versioning, lifecycle и object lock, которые у объектного хранилища встроенные, здесь реализуются в реестре и в коде; удаление blob требует корректного счётчика ссылок, и ошибка в нём даёт либо неудаляемый файл, либо удаление ещё используемого; контроль доступа к файлу целиком на приложении — уровня RLS, работающего без участия разработчика, здесь нет, и п. 8.3 проверяет в том числе этот путь; хранится три представления одного документа (оригинал, DoclingDocument, чанки в Qdrant), объём корпуса на диске кратен исходному.

Не измерено: фактический объём корпуса и доля дубликатов в нём; размер DoclingDocument относительно оригинала на сканах; время sweep на полном корпусе.

Точка ревизии — появление второго узла Data Plane или выход корпуса за пределы одного диска: тогда MinIO за тем же интерфейсом, с переносом ключей без пересчёта.
