# ADR-0031: Streaming (FR-6) — прогресс стадий от MCP-инструмента и потоковый ответ модели чата

Статус: принят  
Deciders: AI Architect  
Дата: 2026-09-24  
Техническая история: ТЗ-ТМ-2026-014, п. 5 (FR-5, FR-6, FR-8, FR-9), 6.1, 7.8, 9.1

## Контекст

FR-6 (приоритет S) требует streaming генерации ответа пользователю. Решения, которые на это влияют, уже приняты:
- **ADR-0020**: текст ответа отдаётся одним `Response::text(...)` после выходных guardrails, стадии — уведомлениями `notifications/progress`. Поток токенов до проверки запрещён.
- **ADR-0030**: выходные проверки (`output_context`, `output_pii`) идут по полному ответу. В последствиях записано, что потоковой выдачи нет.
- **ADR-0024**: на стенде уведомления о прогрессе показывает LibreChat, собранный из ветки с отображением прогресса. Модель чата — тот же vLLM (ADR-0008).

Не было записано, как считать FR-6: закрытым или открытым. Это решение закрывает вопрос.

## Драйверы

- **FR-8 проверяет ответ целиком.** Токен, отданный до проверки, отозвать нельзя.
- **Ответ видит пользователь чата, а не клиент MCP** (7.8, 9.1). Результат вызова инструмента по MCP — одно сообщение. Видимый ответ пишет модель чата уже по этому результату, и чат выводит его потоком.
- **Отдельного интерфейса нет** (9.1). Всё, что пользователь видит во время вызова инструмента, зависит от хоста MCP.
- **Приоритет S.** Требование желательное; сложность и риски решения должны быть соразмерны.

## Варианты

| | Суть |
|---|---|
| **A. Оставить как есть** | Инструмент шлёт стадии через `notifications/progress`, ответ — одним сообщением после guardrails; пользователю ответ выводится потоком модели чата |
| B. Проверенные части ответа в `notifications/progress` | Генерация потоком, выходные проверки по накопленному тексту, наружу — только законченные предложения, прошедшие проверки. Поле прогресса по спецификации MCP — для описания хода работы, а не текста ответа; отображает его только патч стенда; ответ виден дважды: частями в карточке инструмента и в пересказе модели чата |
| C. Поток токенов без проверки, проверка в конце | Прямо нарушает FR-8 и ADR-0020 |

## Решение

**Вариант A.** FR-6 считается закрытым двумя механизмами:

1. **Прогресс стадий от MCP-инструмента.** Пока идёт вызов, `kb-app` шлёт уведомления:
   - «Ищу в документах фрагменты по вопросу…»;
   - по каким сущностям идёт обход графа;
   - «Проверяю, какие фрагменты отвечают на вопрос (найдено: N)…»;
   - «Формирую ответ…».
2. **Потоковый вывод модели чата.** Получив проверенный ответ инструмента, модель чата выводит пользователю свой ответ потоком.

Проверенный ответ уходит одним сообщением, как в ADR-0020. Код не меняется.

## Последствия

Плюс:
- FR-8 не ослабляется: наружу из Платформы не уходит ни одного непроверенного токена;
- в `kb-app` нет правок и нового кода, спецификация MCP не нарушается;
- результат не зависит от того, умеет ли хост показывать текст из уведомлений о прогрессе: поток ответа даёт сам чат.

Минус:
- первый токен ответа пользователь видит только после всего вызова инструмента: поиск, реранк, полная генерация, выходные проверки, затем TTFT модели чата. Для бюджета 6.1 (TTFT P95 ≤ 5 с) это худший случай;
- ответ генерируется дважды — моделью RAG и моделью чата — на одном vLLM (ADR-0009): лишняя нагрузка на генерацию при ≥ 10 пользователях;
- стадии видны только на хосте, который показывает `notifications/progress`: на стенде это патч LibreChat (ADR-0024), у штатного чата Заказчика — не проверено.

Не измерено: TTFT на стороне пользователя (от вопроса до первого токена модели чата) и его P95 при 10 одновременных пользователях.

Точки ревизии:
- нагрузочный тест покажет TTFT P95 > 5 с из-за ожидания инструмента — вариант B;
- чат Заказчика не показывает прогресс — пересмотр, чем пользователь видит ход ответа.
