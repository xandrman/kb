# ADR-0008: LLM Serving — vLLM

Статус: принят  
Deciders: AI Architect  
Дата: 2026-09-19  
Техническая история: ТЗ-ТМ-2026-014, п. 5 (FR-5, FR-6, FR-8, FR-9), 6.1, 6.3, 7.2–7.3, 7.7

## Контекст

Нужен локальный сервер инференса генеративной LLM (7.3, 7.7): OpenAI-совместимый HTTP API, streaming (FR-6), квантование под эталонное железо — EPYC + 4× RTX 3090 (Ampere, 24 GB VRAM каждая, общий бюджет 96 GB на LLM + embedding + reranker + KV-cache, п. 7.2), guided decoding для guardrails (FR-8) и метрики/трейсинг в уже развёрнутый стек Grafana/Tempo/Loki (ADR-0002–0005) для FR-9. Нагрузка — RAG: в промпт на каждый запрос подставляется системная инструкция + найденные графом/вектором чанки (FR-5), диалог многоходовый (история хранится системой диалогов с LLM). Связывающее ограничение — TTFT P95 ≤ 5 с при ≤ 10 одновременных пользователях (6.1, 9.4). У Заказчика — PHP-разработчики, выделенных ML/Data Engineering специалистов в штате нет (2.2); эксплуатацию после сдачи примет эта же команда.

ТЗ (7.3) допускает vLLM, SGLang, TGI или эквивалент — ниже сравниваются два активных лидера 2026 года.

## Драйверы

- **RTX 3090 = Ampere (sm_86), нет аппаратного FP8/NVFP4.** На этом железе оба движка реально работают в INT4/INT8 через Marlin-ядра (AWQ/GPTQ); FP8-чекпоинты либо не ускоряются, либо деквантуются на лету. У vLLM путь AWQ/GPTQ+Marlin — эталонный, задокументированный, воспроизводимый «из коробки». У SGLang аналогичный путь на Ampere закрывают в основном community-рецепты (GitHub), а FP8/W8A8 Marlin для MoE на Ampere на момент исследования — открытый issue в sgl-project (ещё не смержен).
- **RAG-специфика: RadixAttention vs Automatic Prefix Caching.** SGLang кеширует префиксы токен-в-токен в radix-дереве — на prefix-heavy нагрузке (общий system-prompt, повторно используемые чанки между разными запросами) даёт задокументированные 20–40 % снижения TTFT. vLLM с `--enable-prefix-caching` делает то же на уровне блоков (hash по 16–32 токенам) — эффект слабее на «ветвящихся» контекстах, но для линейного many-turn диалога одного пользователя (наш основной кейс — история чата, а не параллельные варианты продолжения) разрыв на практике меньше, чем в синтетических бенчмарках, рассчитанных на массовое пересечение контекстов между многими пользователями одновременно.
- **Штат без ML/Data Engineering (2.2).** Комьюнити vLLM в разы больше, быстрее реакция на issues, больше готовых деплой-рецептов под конфигурацию, близкую к нашей (4× RTX 3090, EPYC) — важно, когда эксплуатацию после сдачи проекта примут PHP-инженеры без профильной ML-экспертизы, а вендорской поддержки в закрытом контуре нет.
- **Observability (FR-9) — паритет.** Оба отдают `/metrics` в формате Prometheus (TTFT, tokens/s, RPS, utilisation) и OpenTelemetry-трейсы «из коробки» — интеграция в существующий Grafana/Tempo/Alloy (ADR-0002–0004) идентична для обоих.
- **Guided decoding — паритет, косвенно к FR-8.** Оба используют XGrammar как backend constrained decoding (JSON/regex/grammar, near-zero overhead). Сами guardrails (FR-8) в ТЗ описаны как отдельные контрольные точки — то есть отдельный сервис/лёгкая модель для PII/prompt-injection, а не часть вызова генеративной LLM; guided decoding пригождается здесь только если такую контрольную точку решат реализовать как LLM-классификатор на том же serving-движке (нужен гарантированно валидный JSON-вердикт). Для выбора между vLLM и SGLang это не различающий фактор — упомянуто как задел на этап проектирования Guardrails-сервиса.
- **Air-gapped (6.3).** vLLM по умолчанию раз в 10 минут отправляет анонимную телеметрию использования во внешний сервис — обязательно отключается (`VLLM_NO_USAGE_STATS=1` / `DO_NOT_TRACK=1`) на этапе развёртывания; фактической утечки не произойдёт и без этой переменной (сеть `kb_internal` без выхода наружу, 6.4), но переменная фиксируется как явная мера defense-in-depth. Аналогичного встроенного «phone home» у SGLang в документации не описано — не проверено практически, зафиксировать отдельно при внедрении.
- Оба — Apache 2.0, self-hosted, без зависимости от облачных API → технологический суверенитет (6.3) не является различающим фактором.

## Варианты

| | Суть |
|---|---|
| **vLLM** | Самый крупный комьюнити и модельный охват; PagedAttention + Automatic Prefix Caching (hash-block); зрелые AWQ/GPTQ+Marlin ядра под Ampere; `/metrics` + OTel из коробки; Apache 2.0 |
| SGLang | RadixAttention — token-level кэш префиксов, лучший TTFT на prefix-heavy/multi-turn нагрузке; квантование под Ampere/consumer GPU — в основном community-рецепты, отдельные пробелы (FP8 Marlin MoE на Ampere) ещё в разработке; Apache 2.0 |
| TGI (Hugging Face) | OpenAI-совместимый API есть, но квантование и throughput на Ampere слабее обоих лидеров, менее активная ветка развития под consumer-GPU multi-TP сценарии — глубоко не рассматривался |

## Решение

**vLLM.** Главный драйвер выбора для MVP — не сырой throughput (на нашем масштабе, ≤ 10 пользователей, с запасом справляются оба), а зрелость квантования именно под RTX 3090/Ampere и размер комьюнити при отсутствии ML-специалистов в штате Заказчика после сдачи проекта.

Обязательные настройки при реализации:
- `--quantization awq` (или `gptq`) + Marlin-ядро — под VRAM-бюджет (7.2);
- `--enable-prefix-caching` — частично закрывает разрыв с RadixAttention на повторных системных промптах/чанках;
- `--tensor-parallel-size` подбирается под фактическую топологию PCIe/NVLink эталонного сервера (пары 3090 с NVLink-мостом — TP внутри пары, PP между парами; финальная схема — по факту `nvidia-smi topo -m` на эталонной машине, раздел Capacity Planning);
- `VLLM_NO_USAGE_STATS=1` (или `DO_NOT_TRACK=1`) — обязателен в окружении контейнера;
- `--otlp-traces-endpoint` → Tempo (ADR-0004), `/metrics` → Alloy/Prometheus (ADR-0002/0003) — сквозной трейс для FR-9 и Sequence Diagram (7.10).

Контейнер `kb_vllm_generate`, сеть `kb_internal`, GPU passthrough через NVIDIA Container Toolkit, без публикации портов хоста — по аналогии с ADR-0001–0006. Версия образа и sha256-digest фиксируются в `infra/main.tf` при реализации.

Точка ревизии решения: если по факту нагрузочного тестирования (п. 8, критерии приёмки) TTFT P95 на прод-подобной RAG-нагрузке (общий system-prompt и пересекающиеся чанки между пользователями) превышает 5 с из-за cache-miss на повторных префиксах — переоценить миграцию на SGLang как «шов расширения» (6.5); архитектурно замена ограничена одним микросервисом LLM-serving за HTTP (7.7), контракт (OpenAI-совместимый API) не меняется.

## Последствия

Плюс:
- Наибольший модельный охват и зрелость quantization-пути под конкретно наш GPU — ниже риск «неожиданных» багов на этапе внедрения силами команды без ML-профиля;
- `/metrics` + OTel трейсинг «из коробки» — не требует доп. адаптеров для интеграции в Grafana/Tempo (ADR-0002–0004);
- XGrammar guided decoding — структурированный вывод для guardrails (FR-8) без заметных накладных расходов;
- Явная точка ревизии решения зафиксирована — переход на SGLang не потребует переделки конвейера (RAG-контракт не завязан на конкретный serving-движок).

Минус:
- На prefix-heavy сценариях (несколько пользователей одновременно обсуждают один документ/SKU) TTFT у vLLM может быть на 20–40 % выше, чем у SGLang с RadixAttention — снижается запас по п. 6.1 при росте пилота сверх 10 пользователей;
- Обязательна ручная проверка/отключение телеметрии usage-stats на этапе развёртывания (иначе — попытка исходящего сетевого обращения, недопустимая по 6.3);
- 4-way TP без единого NVLink-моста (3090 поддерживает NVLink только парами) требует ручной настройки гибридной TP+PP-топологии под фактическую разводку PCIe эталонного сервера — не «из коробки», требует профилирования на этапе Capacity Planning (7.10).
