# ADR-0036: Выделенный сервис секретов (Vault) в MVP не внедряется

Статус: принят  
Deciders: AI Architect  
Дата: 2026-09-25  
Техническая история: ТЗ-ТМ-2026-014, п. 2.2, 6.3, 6.4, 7.10, 10

## Контекст

ТЗ (6.4) требует хранить секреты в выделенном сервисе (Vault) с мастер-ключом и описать порядок владения ключом. Такого сервиса в стеке нет. Секреты задаются переменными Terraform: пароли PostgreSQL и Neo4j, `APP_KEY`, секреты клиентов Keycloak, ключи LibreChat. Из переменных они попадают в окружение контейнеров, а значит, в `docker inspect` и в state Terraform. Секреты клиентов Keycloak и seed-пароль подставляются в импортируемый realm через `templatefile`. На выделенный сервис уже рассчитывают ADR-0007 и ADR-0014 (пароли СУБД) и точки ревизии ADR-0032 и ADR-0033.

Развёртывание — Terraform с docker-провайдером на одном сервере (ADR-0001). У Docker Engine нет порядка запуска контейнеров. `depends_on` с `wait = true` в Terraform ждёт healthcheck зависимости, но только во время `terraform apply`. Контейнеры, которые `dockerd` поднимает по restart policy после перезагрузки, стартуют одновременно и без учёта зависимостей.

Внедрение сервиса секретов на базе OpenBao было спроектировано и начато. До конца срока успели развернуть и проверить на стенде только сервер. Агент и перевод потребителей не сделаны. Частичное развёртывание удалено, стенд и репозиторий возвращены в исходное состояние. Этот ADR фиксирует решение не внедрять сервис на демонстрационном стенде MVP. Он также сохраняет выбранную для следующей стадии схему на OpenBao, результаты её проверок и трудности, с которыми столкнулись.

## Драйверы

- **Секреты не попадают в git, `tfvars`, state Terraform и `docker inspect` (6.4).**
- **Мастер-ключ и порядок владения им (6.4).** На демонстрационном стенде сервис после перезагрузки поднимается без оператора. В контуре Заказчика ключ отделён от данных.
- **Лицензия, совместимая с закрытым коммерческим использованием (6.3, 10 — артефакт 2).**
- **Без секрета процесс не работает на значениях по умолчанию.** Сбой доставки виден сразу, а не превращается в сервис, который выглядит исправным и работает неправильно.
- **Штатные механизмы вместо самописной обвязки (2.2).** Сопровождение — PHP-команда без DevOps-специалиста. Обёртки в `command` и entrypoint отвергнуты как обходные решения.
- **Установка без ручных шагов.** `terraform apply` на чистом сервере даёт работающий стек. Оператор не выполняет инициализацию и не переносит токены между шагами.
- **Срок MVP и работающий стенд.** Внедрение затрагивает все сервисы с секретами. Незавершённый перевод оставляет стенд в смешанном состоянии, где часть секретов в OpenBao, часть в `tfvars`.

## Варианты

| | Суть |
|---|---|
| A. Внедрить OpenBao по схеме ниже | Выполняет 6.4. Цена — два новых контейнера, учётные файлы на хосте, перевод всех сервисов с секретами и миграция их текущих значений. До срока не завершено |
| **B. Не внедрять сервис секретов в MVP** | Секреты остаются переменными Terraform в `terraform.tfvars`. Требование 6.4 в части хранения секретов не выполняется |

Ниже — варианты, рассмотренные внутри A. Жирным выделен выбор для схемы A, а не решение этого ADR.

**Сервер секретов**

| | Суть |
|---|---|
| A. HashiCorp Vault Community | Лицензия BSL 1.1 (с 1.15). Auto-unseal через HSM (PKCS#11) — только в Enterprise |
| **B. OpenBao** | Форк Vault в Linux Foundation, лицензия MPL 2.0. API, CLI, агент и шаблоны совместимы с Vault. `seal "static"` и `seal "pkcs11"` бесплатны |

**Доставка секрета в процесс**

| | Суть |
|---|---|
| **A. Общий агент, файлы в tmpfs** | Один контейнер агента рендерит файлы в tmpfs-тома. Потребитель монтирует свой том только на чтение и читает файл штатным механизмом приложения |
| B. Переменные окружения из файла через обёртку `command` или entrypoint (`set -a; . file`) | Правка запуска каждого контейнера. Отвергнуто как обходное решение |
| C. Агент в режиме process supervisor | Агент — PID 1 контейнера: запускает приложение после получения секретов, перезапускает при смене. В OpenBao режим в public beta. Бинарник `bao` (≈180 МБ) встраивается в образ, секреты попадают в окружение процесса |
| D. Приложение читает API OpenBao | Код Платформы привязан к OpenBao. Сторонние сервисы так не умеют |
| E. Docker Swarm + драйвер-плагин секретов | Переход с `docker_container` на `docker_service`. Плагин для OpenBao — молодой сторонний проект |
| F. Kubernetes + injector | Замена ADR-0001, GPU в Kubernetes на одном узле |

**Распечатывание (unseal)**

| | Суть |
|---|---|
| A. Ручной, Shamir | После каждого рестарта сервиса стенд стоит до прихода оператора |
| **B. `seal "static"`: ключ в файле на хосте** | Auto-unseal без оператора. Ключ лежит рядом с данными и от кражи диска не защищает |
| C. `seal "pkcs11"`: HSM Заказчика | Auto-unseal, ключ вне сервера. Нужен HSM |
| D. Transit через второй сервер | Проблема переходит ко второму серверу |
| E. Dev-режим | Данные в памяти, после рестарта теряются |

**Первоначальная настройка**

| | Суть |
|---|---|
| A. `bao operator init` + провайдер `vault` в основном модуле Terraform | Три шага `apply` с ручной инициализацией. Каждый `plan` всего стека требует работающий сервер и токен |
| B. То же, но отдельным модулем `infra/openbao-config/` | Основной стек без токена. Остаются ручная инициализация и токен для модуля настройки |
| **C. Самоинициализация OpenBao (self-init)** | Блоки `initialize` в конфигурации сервера выполняются им самим при первом старте на пустом хранилище. Root-токен никому не выдаётся и отзывается. Требует auto-unseal |
| D. Разовый контейнер с CLI `bao` | Токен и начальные значения попадают в state Terraform |

**Процесс, стартовавший раньше секретов**

| | Суть |
|---|---|
| **A. Явное падение + restart policy** | Без секрета процесс завершается с понятной ошибкой, Docker перезапускает его, пока агент не доставит файл |
| B. systemd-юниты с `After=`/`Requires=` | Настоящий порядок запуска, но запуск контейнеров уходит из Terraform и Docker в ОС хоста |
| C. Скрипт ожидания в entrypoint или `command` | Своя обвязка в каждом контейнере |

## Решение

**Вариант B.** Выделенный сервис секретов (Vault, 6.4) в MVP не внедряется.

- Решение касается только демонстрационного стенда MVP. Для следующей стадии развития путь уже известен: выбран OpenBao по схеме варианта A, и эта схема частично проверена (раздел «Что сделано и проверено»). Там сервис секретов внедряется отдельным ADR, который замещает этот.
- Секреты остаются переменными Terraform: значения в `terraform.tfvars`, передача контейнерам — через переменные окружения и `templatefile`, как до этого ADR. `terraform.tfvars` и state исключены из git (`.gitignore`).
- Требование 6.4 «хранение секретов в выделенном сервисе (Vault) с мастер-ключом» в MVP не выполняется. Отклонение фиксируется этим ADR и должно быть раскрыто Заказчику при приёмке.
- Упоминания пароля «из Vault» в ADR-0007 и ADR-0014 остаются нереализованными: пароли СУБД берутся из `terraform.tfvars`.
- Точки ревизии ADR-0032 (секреты в `docker inspect`) и ADR-0033 (PKI-движок) не наступают.
- Схема варианта A, результаты проверок и найденные трудности описаны ниже как основа для внедрения на следующей стадии.

## Схема варианта A (не реализована)

**OpenBao, общий агент с файлами, `seal "static"` на стенде с переходом на `pkcs11` в контуре Заказчика, самоинициализация, явное падение без секрета.**

**Сервер `kb-openbao`**
- Хранилище `raft`, один узел, том на хосте. Порт не публикуется, доступ только из `kb-internal`.
- Учётные файлы на хосте вне git (`infra/openbao/credentials/`): ключ `seal "static"`, `secret_id` агента, пароль администратора. Их создаёт Terraform (`terraform_data` с `local-exec`, `openssl rand`), только если файла ещё нет. Значения в state не попадают.
- Самоинициализация при первом старте:
  - монтирует KV v2 в `kv/`;
  - создаёт политики агента и администратора;
  - создаёт AppRole агента с заданным `role_id` и `secret_id` из учётного файла;
  - создаёт администратора `userpass` с паролем из учётного файла;
  - заполняет все секреты стека случайными значениями (`sys/tools/random` → KV).
- Ключ KV — сервис-владелец секрета: `kv/kb-app`, `kv/kb-postgres`, `kv/kb-neo4j`, `kv/kb-keycloak`, `kv/kb-librechat`. Один пароль лежит в одном месте, и сервер (`NEO4J_AUTH`) и клиент (`NEO4J_PASSWORD`) читают его оттуда.

**Порядок владения ключами (6.4)**
- Root-токен не выдаётся никому. Администратор (`userpass`, ИБ Заказчика) — не root.
- Recovery-ключи выпускает администратор после установки (`sys/rotate/recovery/init`). Хранит их ИБ вне сервера.
- Root-токен по recovery-ключу выпускается двумя путями:
  - штатно: токен администратора + recovery-ключ;
  - аварийно, если пароль администратора потерян: recovery-ключ через unix-сокет внутри контейнера, где разрешён неаутентифицированный generate-root. Попасть к сокету можно только через `docker exec`.

**Агент `kb-openbao-agent`**
- Вход по AppRole; `max_backoff = "30s"`; `exit_on_retry_failure = true`.
- Шаблоны рендерятся в два прохода: Terraform `templatefile` подставляет параметры стенда, агент — секреты. Каждый файл рендерится целиком или не рендерится вовсе.

**Потребители**

| Потребитель | Механизм |
|---|---|
| `kb-app`, воркеры | `.env` Laravel — ссылка на файл в tmpfs. Отдельные шаблоны для приложения и воркеров: у воркеров другой транспорт OTLP |
| `kb-grafana` | `$__file{...}` |
| `kb-postgres`, `kb-neo4j` | `*_FILE` (поведение без файла не проверено) |
| `kb-keycloak` | агент рендерит импортируемый realm |
| `kb-librechat` | `.env` в `/app` |

**Явное падение без секрета:** проверка в Laravel в `afterLoadingEnvironment` (`.env` — ссылка на отсутствующий файл → исключение). Grafana с `$__file` завершается сама.

## Что сделано и проверено

На временных контейнерах (OpenBao 2.7.0; стенд не затрагивался):
- `seal "static"`: сервер после `docker restart` распечатывается сам;
- самоинициализация:
  - на пустом хранилище сервер инициализировался без `operator init`;
  - KV, политики, AppRole и `userpass` созданы;
  - `APP_KEY` в формате `base64:` + 32 байта, пароли нужной длины;
  - после рестарта блоки повторно не выполняются;
- агент:
  - входит по `role_id` из конфигурации и `secret_id` из файла, рендерит `.env`, Laravel разбирает его, значение со спецсимволами `$`, `\`, `#` в одинарных кавычках доходит без искажений;
  - стартовав раньше сервера, рендерит файлы через 17 с после его подъёма;
  - после рестарта сервера работает без повторного входа;
  - смена секрета доходит до файла за 8 с при интервале перечитывания 10 с, по умолчанию — за 5 мин;
  - при отсутствующем секрете с `exit_on_retry_failure` завершается с кодом 1, не оставляя частичных файлов;
- recovery-ключ выпускается через `sys/rotate/recovery/init`; оба пути выпуска root-токена по нему работают; на TCP-порту неаутентифицированный generate-root закрыт (`405`);
- без `.env` `migrate` завершается ошибкой, если в окружении контейнера задан `DB_CONNECTION=pgsql`; `queue:work` при этом тоже падает сразу;
- Grafana с `$__file` без файла завершается с кодом 1.

На стенде: сервер `kb-openbao` развёрнут Terraform, прошёл самоинициализацию, распечатывался после рестарта; recovery-ключ выпущен. Затем всё удалено.

## Трудности

**Требования и архитектура**
- ТЗ называет сервис «Vault». OpenBao обоснован как совместимый форк, но согласование с Заказчиком не проводилось.
- Ручной unseal несовместим с автономной работой стенда. Auto-unseal без HSM или KMS держит ключ рядом с данными, и это приходится оформлять как принятый риск.
- В Docker нет порядка запуска. Ожидание зависимостей в инструментах развёртывания действует только во время их работы, а после перезагрузки все контейнеры стартуют одновременно. Отсюда правило «без секрета — явное падение».
- Доставка без правки `command` потребовала искать штатный механизм для каждого сервиса. У разных сервисов он разный, и не все умеют читать секреты из файла (LibreChat не поддерживает `*_FILE`).
- Самоинициализация выполняется один раз, поэтому в неё пришлось сразу заложить все секреты стека. Всё добавленное позже вносится только через API.
- Действующий стенд уже инициализирован со старыми значениями: пароли в томах СУБД, клиенты в базе Keycloak, `APP_KEY`, ключи шифрования LibreChat. Случайные значения самоинициализации им не подходят. Нужна отдельная миграция: записать в KV текущие значения до перевода потребителей.

**Найденные при проверках ловушки**
- Laravel без `.env` не падает: `DB_CONNECTION` по умолчанию `sqlite`, и `migrate --force` успешно создаёт пустую SQLite-базу в контейнере и накатывает все миграции. Сервис выглядел бы исправным на пустой базе.
- Grafana с `GF_*__FILE` при отсутствующем файле стартует с пустым значением: `run.sh` выводит ошибку и продолжает. Штатно падает только вариант `$__file{...}`.
- tmpfs-том очищается, когда его перестаёт использовать последний контейнер. Если агент остановлен, перезапущенный потребитель остаётся без секретов.
- Долгоживущие процессы (`queue:work`) читают секреты один раз при старте. После смены секрета их нужно перезапускать (`queue:restart`).
- Двухпроходные шаблоны: `${` в комментарии ломает `templatefile`, а `{{ }}` в комментарии ломает шаблонизатор агента. Каждую ошибку поймал только свой проход.
- Агент без `exit_on_retry_failure` повторяет рендер бесконечно: контейнер жив, файла нет. Опция не действует на вход: при недоступном сервере агент ждёт бесконечно, и пауза между попытками растёт до 5 мин, если не задать `max_backoff`.
- В OpenBao 2.x удалён `storage "file"`. Ключ `seal "static"` из `openssl rand -hex 32` не принимается, работают 32 сырых байта.
- В именах запросов самоинициализации нельзя использовать дефис: в шаблоне `.responses.random.app-key` дефис разбирается как минус.
- Самоинициализация не создаёт recovery-ключей. С версии 2.6 generate-root требует токен, так что recovery-ключ без пароля администратора бесполезен. Для этого случая понадобился отдельный аварийный unix-сокет.
- Провайдеру `vault` в Terraform нужны работающий сервер и токен на каждый `plan`. Поэтому варианты A и B первоначальной настройки отвергнуты в пользу самоинициализации.
- `precondition` с `fileexists` выполняется при `plan`, раньше, чем `terraform_data` создаёт файлы. На чистом сервере первый `apply` упал бы.
- Полный `terraform plan` пересобрал бы образ `kb-app`: хэш образа включает неотслеживаемые файлы `backend/`. Все изменения стенда пришлось применять с `-target`.
- Самоинициализация срабатывает только на пустом хранилище. Сервер, уже инициализированный вручную, пришлось пересоздавать вместе с томом.

**Трудности процесса**
- Решение несколько раз менялось по ходу:
  - доставка: переменные окружения → обёртка `command` → process supervisor → файлы со штатными механизмами;
  - первоначальная настройка: ручная инициализация → провайдер Terraform → самоинициализация;
  - recovery-ключи: без них → выпуск администратором плюс аварийный сокет.

  Черновик ADR переписывался вслед за этими изменениями.
- Часть утверждений при проектировании оказалась неверной и была исправлена после проверки или замечания:
  - «Grafana без файла не стартует» — для `__FILE` неверно;
  - `storage "file"` в OpenBao — удалён;
  - формулировка про `depends_on` в Docker Compose — неточная;
  - пересказ точки ревизии ADR-0032 — ошибочный;
  - заявление о проверке шаблонов во временных контейнерах — на деле проверялся только первый проход.
- Тестовые сценарии не раз давали ложный результат:
  - проверка на томе, где файл ещё лежал;
  - `bao write` без `-force`;
  - разбор ответа не по той структуре;
  - сохранённый токен администратора, подставленный CLI вместо пустой переменной.

  Результаты выше получены пошаговыми прогонами с проверкой каждого ответа.
- Большая часть времени ушла на проверку поведения на временных контейнерах. Без неё в решение попали бы по меньшей мере пустая SQLite-база, пустой секрет Grafana и неработающий recovery-ключ.

## Последствия

Плюс:
- стенд не усложняется незавершённой миграцией: все секреты в одном месте, развёртывание и сопровождение не меняются;
- для следующей стадии выбор уже сделан — OpenBao. Схема спроектирована и частично проверена на временных контейнерах и на стенде, а ловушки, найденные проверкой, перечислены выше. Внедрение начнётся не с исследования, а с реализации.

Минус:
- требование 6.4 (выделенный сервис секретов с мастер-ключом) на демонстрационном стенде не выполнено;
- секреты по-прежнему передаются через `terraform.tfvars` и видны в `docker inspect` и state;
- стенд и репозиторий возвращены в исходное состояние: контейнер, том и учётные файлы OpenBao удалены, конфигурация не закоммичена. Схему варианта A придётся реализовать заново по этому ADR.

Что нужно решить до внедрения на следующей стадии:
- согласование OpenBao вместо Vault с Заказчиком (6.4);
- поведение `POSTGRES_PASSWORD_FILE` и `NEO4J_AUTH_FILE` без файла;
- перечитывание `.env` воркерами php-fpm без рестарта (проверялось только новым процессом CLI);
- порядок миграции текущих секретов стенда в KV.

Отклонение от 6.4 касается приёмки MVP (8, 10 — артефакт 2) и должно быть согласовано с Заказчиком вместе с планом внедрения OpenBao на следующей стадии.

Точка ревизии — переход к следующей стадии: внедрение OpenBao по схеме варианта A отдельным ADR, замещающим этот.
