# ADR-0032: Логи контейнеров в Loki — драйвер syslog Docker по UDP в Alloy через отдельную сеть `kb-logs`

Статус: принят  
Deciders: AI Architect  
Дата: 2026-09-24  
Техническая история: ТЗ-ТМ-2026-014, п. 2.2, 5 (FR-8, FR-9), 6.3, 6.4, 7.9, 8

## Контекст

Критерий приёмки 8.4 требует показать логи LLM-сервера, FR-9 — связать их с трейсом запроса. ADR-0005 решил собирать контейнерные логи через `loki.source.docker`. Реализован пока только сбор логов nginx: `kb-nginx` пишет файлы на том `kb-nginx-logs`, Alloy читает его через `loki.source.file`. Логи остальных контейнеров в Loki не попадают.

Частично замещается ADR-0005: способ сбора контейнерных логов (`loki.source.docker`) и перечень источников. Выбор Loki, срок хранения и метки остаются в силе. Производное поле Grafana ищет `trace_id` не регуляркой по тексту строки, а в структурированных метаданных записи.

## Драйверы

- **8.4 и FR-9.** Нужны логи vLLM, а для разбора ответа — логи `kb-app` и воркеров с `trace_id`, в одном месте с трейсами.
- **Сегментация (6.4).** `loki.source.docker` читает логи через API Docker. Кто владеет сокетом Docker, тот фактически владеет хостом: может создать привилегированный контейнер, выполнить команду в любом другом, прочитать переменные окружения с секретами. Прокси только на чтение не закрывает `inspect`, а с ним и секреты.
- **Подлинность записи.** Запись с именем сервиса должна приходить от этого сервиса, а не от соседнего контейнера.
- **ПДн и коммерческая тайна не попадают туда, где их не ждут (6.4, 152-ФЗ).** Журнал guardrails не содержит ПДн (ADR-0030), и логи тоже не должны: Loki доступен всем с доступом к Grafana.
- **Один способ для всех сервисов.** Команда без DevOps в штате (2.2): лучше один механизм, чем настройка вывода в файл у каждого сервиса.
- **Air-gapped (6.3):** без новых образов и плагинов хоста.

## Варианты

| | Суть |
|---|---|
| A. `loki.source.docker`, сокет Docker в Alloy | Штатно по ADR-0005; компрометация Alloy — root на хосте |
| B. `loki.source.docker` через прокси сокета только на чтение | POST и exec закрыты, но `inspect` с переменными окружения остаётся; лишний контейнер с сокетом |
| C. Файлы `/var/lib/docker/containers/*/*-json.log` в Alloy на чтение | Без API; том открывает логи всех контейнеров хоста, имени контейнера в файлах нет |
| D. Каждый сервис пишет лог в файл на своём томе | Без API; у каждого сервиса своя настройка и ротация. Loki, Tempo, Prometheus и DCGM писать в файл не умеют |
| E. OTLP-логи от сервисов | У vLLM, docling, СУБД экспорта логов в OTLP нет |
| **F. Драйвер логов Docker `syslog` → `loki.source.syslog` в Alloy** | Логи отправляет dockerd, сервисы не меняются; настройка — `log_driver` и `log_opts` в Terraform |

## Решение

**Вариант F: syslog по UDP.**

**Транспорт.**
- Драйвер `syslog` с опциями `syslog-format=rfc5424micro` и `tag={{.Name}}`: имя контейнера приходит в поле `APP-NAME`, время — с микросекундами. stdout приходит с уровнем `info`, stderr — с уровнем `err`.
- UDP, а не TCP. При TCP dockerd подключается к Alloy при старте контейнера, и пока Alloy недоступен, не стартует ни один контейнер Платформы: сборщик логов стал бы точкой отказа для запуска всего стека. По UDP запуск ни от чего не зависит; цена — возможная потеря строк при всплесках.
- GELF не выбран: приёмник Alloy для него работает только по UDP и ничего не добавляет к syslog.

**Адрес Alloy — отдельная сеть `kb-logs`.**
- Логи отправляет dockerd на хосте. Имён контейнеров он не знает: их разрешает DNS Docker, который есть только внутри контейнеров. Адрес попадает в конфигурацию контейнера при создании. Нужен IP, который не меняется при пересоздании Alloy.
- Сеть `kb-logs` — `internal`, с явно заданной подсетью (переменная Terraform, по умолчанию `10.254.254.0/24`, вне диапазона, из которого Docker выделяет сети автоматически). Хост — шлюз, `.1`; Alloy — фиксированный адрес `.2`. Порт `1514/udp`. В `kb-logs` нет никого, кроме Alloy.
- В `kb-internal` фиксированный адрес не ставится: Docker разрешает его только в сети с явно заданной подсетью, а её добавление пересоздаёт `kb-internal` со всеми контейнерами. Кроме того, писать на адрес Alloy там могли бы все контейнеры сети.
- Подсеть вынесена в переменную: на площадке Заказчика она может пересечься с его сетями.

**Подлинность записи.** На стенде проверено: до адреса Alloy в `kb-logs` доходят пакеты с хоста, но не доходят ни из обычной сети Docker (как `kb-dmz`), ни из другой сети `internal` (как `kb-internal`). Записи может отправлять только dockerd. Вторая линия — Alloy оставляет только записи с адреса шлюза `kb-logs` (`__syslog_connection_ip_address`). Проверка стоит в отдельном `loki.relabel`: правило `keep` в `relabel_rules` самого источника сбрасывает только метки, а запись пропускает.

**Alloy.**
- `loki.source.syslog`: протокол `udp`, слушает только адрес Alloy в `kb-logs`. В `kb-internal` порта нет.
- Метки:
  - `service_name` — из `APP-NAME`;
  - `stream` — `stdout` при уровне `info`, `stderr` при уровне `err`.
- В `loki.process` по `service_name`:
  - многострочные записи (трассировки стека Python и PHP) склеиваются в одну: Docker отправляет каждую строку отдельной записью;
  - строки опроса `/metrics` и `/health` отбрасываются — Prometheus опрашивает каждый vLLM раз в 15 с (ADR-0013);
  - `trace_id` уходит в структурированные метаданные, не в метку (ADR-0005): из текста `trace_id=…` или из JSON `"trace_id":"…"`, в котором Laravel пишет его в каждую запись внутри трейса.
- Сам Alloy остаётся на `json-file`: отправлять свои логи через себя по syslog он не может. Свои логи он пишет в Loki блоком `logging { write_to }`.

**Источники.** Драйвер `syslog` у всех контейнеров Terraform, кроме:
- `kb-alloy` — см. выше;
- `kb-librechat` и `kb-librechat-mongo` — стенд вне поставки (ADR-0024). Сообщения пользователей в них не маскированы: маскирование `input_pii` (ADR-0030) стоит в `kb-app`, а не в чате. MongoDB пишет значения фильтров в лог медленных запросов, а скрыть их в Community нельзя. Остаются на `json-file`;
- `kb-nginx` — как сейчас, файлы на томе `kb-nginx-logs`;
- разовые init-контейнеры (`kb-hf-cli-*`, `kb-certbot-init`, `kb-documents-init`) — их вывод Terraform показывает при apply. Смена драйвера пересоздала бы их и запустила заново, в том числе загрузку моделей.

У `kb-postgres` дополнительно `log_error_verbosity=terse` и `log_min_error_statement=panic`: в лог не попадают текст запросов и блок DETAIL, где PostgreSQL печатает значения из строк.

**`docker logs`.** Работает при драйвере `syslog` через dual logging (проверено на стенде, Docker 29.5): Docker хранит локальную копию, по умолчанию до 5 файлов по 20 МБ на контейнер.

## Последствия

Плюс:
- 8.4 закрыт: логи vLLM и приложения в Loki, строки `kb-app` связаны с трейсом по `trace_id`;
- собираются все сервисы, включая Loki, Tempo, Prometheus и DCGM, которые пишут только в stderr;
- ни у одного контейнера нет доступа к API Docker, записи в Loki может отправить только dockerd;
- сервисы и их образы не меняются: вся настройка — `log_driver` и `log_opts` в Terraform, новый сервис получает сбор логов теми же строками;
- ротацией занимается Docker (локальная копия ограничена) и Loki (срок хранения), а не каждый сервис.

Минус:
- UDP может терять строки при всплесках; ошибки отправки dockerd не показывает;
- dockerd на хосте и приёмник в контейнере связаны адресом из переменной Terraform: при смене подсети пересоздаются все контейнеры;
- записи длиннее предела датаграммы UDP обрезаются;
- логи Loki проходят через сам Loki: когда он недоступен, его логи есть только в `docker logs`;
- `kb-nginx` собирается отдельным способом (файлы), это исключение из единого механизма.

Не измерено: доля потерянных строк по UDP при обработке пилотного корпуса, когда восемь воркеров графа пишут одновременно; объём логов на диске Loki за 30 дней хранения.

Точки ревизии:
- потери строк на замере заметны — syslog по TCP с `mode=non-blocking` и запуском Alloy до остальных контейнеров;
- Vault (6.4) выведет секреты из переменных окружения — вариант B снова можно рассмотреть.
