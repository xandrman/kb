# ADR-0035: Эмбеддер без CUDA-графов и с подобранным конфигом MoE-ядер (частичное замещение ADR-0010)

Статус: принят  
Deciders: AI Architect  
Дата: 2026-09-24  
Техническая история: ТЗ-ТМ-2026-014, п. 5 (FR-3, FR-4), 6.1, 6.2, 7.2, 7.10

## Контекст

`kb-vllm-embedding` (ADR-0010) периодически падал под нагрузкой граф-воркеров: движок завершался с `CUDA error: an illegal memory access was encountered`, контейнер перезапускался, запросы в этот момент получали 500. Сбой воспроизводится детерминированно одним запросом с несколькими сотнями коротких входов, а под обычной нагрузкой возникает, когда восемь граф-воркеров одновременно векторизуют имена сущностей и планировщик собирает их в один батч.

Причина — рабочий буфер MoE-ядер в vLLM. Промежуточные тензоры экспертов берутся из одного общего буфера, размер которого определяется первым прогоном. Для pooling-модели с MoE прогрев при старте размечает его примерно на 32 токена (1 МБ при ~30 КБ на токен для E=64, top_k=4, hidden 1536, intermediate 1280): профилирующий прогон на полный батч до MoE-буфера не доходит, размер задаёт захват CUDA-графов. Батч крупнее ~32 токенов требует большего буфера:

- в 0.29.0 буфер пересоздаётся, а захваченные CUDA-графы продолжают писать по старому адресу — illegal memory access;
- в 0.30.0 буфер после захвата графов блокируется, и тот же батч завершает движок с `Workspace is locked but allocation ... requires 3.25 MB, current size is 1.00 MB`.

Поведение одинаково в обоих раннерах vLLM (Model Runner V1 и V2): переход на 0.30.0 и `VLLM_USE_V2_MODEL_RUNNER=0` проверены на стенде и падение не устраняют. Штатной настройки размера буфера в vLLM нет.

Отдельно оставался невыполненным п. 5 ADR-0010: подобранного конфига fused_moe для `E=64,N=1280` на RTX 3090 нет, vLLM работает на параметрах Triton по умолчанию (`Using default MoE config`).

## Драйверы

- **Стабильность под реальными батчами.** Индексация (FR-3) и слияние синонимов графа (FR-4) отправляют пакеты в сотни входов; движок не должен падать на корректном запросе.
- **Бюджет TTFT (6.1).** Векторизация запроса входит в 5 секунд; цена обхода на одиночном запросе должна оставаться в миллисекундах.
- **Одна версия vLLM на стенде.** Все три движка на одном образе — одна точка пиннинга (ADR-0010, п. 3) и один образ в закрытом контуре.
- **Производительность измеряется, а не предполагается (7.10).** Эффект обхода и подбора ядер фиксируется замером на целевой карте.

## Варианты

| | Суть |
|---|---|
| A. Обновить vLLM до 0.30.0 | Падение становится явной ошибкой вместо порчи памяти, но остаётся; появляется вторая версия vLLM на стенде |
| B. Model Runner V1 (`VLLM_USE_V2_MODEL_RUNNER=0`) | Буфер размечается и блокируется на те же 1 МБ — падение сохраняется |
| C. Патч vLLM: резервировать буфер под `max_num_batched_tokens` | Лечит симптом во внутреннем API без гарантий совместимости; свой образ и перенос патча на каждую версию |
| **D. `--enforce-eager` на 0.29.0** | Без CUDA-графов захват не выполняется, буфер не блокируется и растёт по запросу; писать по старому адресу нечему |

## Решение

**Вариант D.**

1. **`--enforce-eager` для `kb_vllm_embedding`**, версия vLLM остаётся 0.29.0 — та же, что у генератора и реранкера. Рабочий буфер MoE растёт по фактическому батчу: до ~245 МБ на 8192 токенах, что укладывается в запас 3.6 ГиБ на карте эмбеддера (ADR-0010).
2. **Подобранный конфиг MoE-ядер** — `infra/vllm-embedding/E=64,N=1280,device_name=NVIDIA_GeForce_RTX_3090.json`. Получен `benchmark_moe.py --tune` из образа v0.29.0 (Triton 3.7.1) на RTX 3090 с лимитом 200 Вт по размерам батча 1–8192, включая 6144 и 8192 под `max_num_batched_tokens`. Подбор занял 14.4 часа.
3. **Способ поставки конфига.** Файл хранится в репозитории и подкладывается в контейнер через `upload` Terraform в `/moe-configs`; путь передаётся переменной `VLLM_TUNED_CONFIG_FOLDER`. Этим замещается формулировка п. 5 ADR-0010 «вшивается в образ на этапе сборки»: образ vLLM остаётся стоковым, а конфиг, как и веса, не требует сети в закрытом контуре. Остальное в п. 5 ADR-0010 сохраняет силу.
4. **Условия повторного подбора:** смена версии vLLM или Triton, модели GPU или её лимита мощности, а также модели эмбеддингов. Имя файла привязано к форме MoE и модели карты, поэтому vLLM молча вернётся к параметрам по умолчанию, если любое из этого разойдётся — признак в логе `Using default MoE config`.

## Замеры

Карта эмбеддера, профиль ADR-0010: `vllm bench serve --backend openai-embeddings`, вход 1024 токена, батч 32, 50 запросов, c=1. Одиночный запрос — медиана 30 запросов с query-префиксом.

| Конфигурация | Пропускная способность | E2EL медиана / P99 | Одиночный запрос |
|---|---|---|---|
| 0.29.0, CUDA-графы, MoE по умолчанию (ADR-0010) | 10 560 ток/с | 3 058 / 3 075 мс | 28.6 мс |
| 0.29.0, eager, MoE по умолчанию | 10 697 ток/с | 3 016 / 3 045 мс | 48.2 мс |
| **0.29.0, eager, подобранный MoE** | **11 246 ток/с** | **2 867 / 2 910 мс** | **49.4 мс** |

Пакет из 300 коротких входов, 64 входа по ~8K токенов и 8 параллельных клиентов по 40 одиночных запросов проходят без ошибок и перезапусков во всех eager-конфигурациях. Векторы не меняются: размерность 1536, норма 1.0, косинус русско-английской пары 0.667.

## Последствия

Плюс: движок эмбеддингов больше не падает на батчах из сотен входов, векторизация имён сущностей снова идёт пакетами; все три движка на одной версии vLLM; п. 5 ADR-0010 выполнен и измерен — +5.1 % пропускной способности на батчах индексации; конфиг ядер воспроизводим и лежит в репозитории.

Минус: одиночный запрос медленнее на ~20 мс (28.6 → ~49 мс) — меньше 0.5 % бюджета TTFT по 6.1, но это прямая цена отказа от CUDA-графов, и подобранный конфиг её не компенсирует: в eager-режиме одиночный запрос ограничен не MoE-ядром; первый крупный батч после каждого перезапуска эмбеддера на ~2 с медленнее из-за разовой JIT-компиляции ядра; подбор конфига стоит ~14 часов карты и повторяется при каждом условии из п. 4 решения; обход держится на поведении vLLM, которое не закреплено ни документацией, ни тестом.

Точка ревизии — версия vLLM, в которой прогрев pooling-модели с MoE резервирует рабочий буфер под `max_num_batched_tokens`. Проверка: без `--enforce-eager` запрос с 300 короткими входами проходит, в логе нет роста буфера после захвата графов. Тогда `--enforce-eager` снимается, конфиг MoE подбирается заново под новую версию, замеры повторяются по той же таблице. Вклад эмбеддера в TTFT и пик VRAM при 16 последовательностях по-прежнему подлежат замеру в Capacity Planning (7.10, ADR-0016).
