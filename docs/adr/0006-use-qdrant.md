# ADR-0006: Vector DB — Qdrant

Статус: принят  
Deciders: AI Architect  
Дата: 2026-09-19  
Техническая история: ТЗ-ТМ-2026-014, п. 7.5

## Контекст

Нужна векторная БД для гибридного поиска (FR-3, FR-5): 125–500 документов → ~10 000–50 000 чанков, embedding 1024-d, ≤ 10 одновременных пользователей. Ключевое: RBAC на уровне чанков (фильтрация по грифу доступа при поиске, FR-7) и интеграция из PHP 8.x.

## Драйверы

- **Фильтрация по правам доступа на этапе поиска.** При поиске похожих чанков система должна учитывать гриф доступа (`access_level`, `department`). В Qdrant это работает «внутри» алгоритма поиска: при обходе графа векторов каждый кандидат проверяется по правам — пользователь без доступа к «конфиденциальным» документам просто не видит их в результатах, а не получает 10 совпадений из 50 и 40 отброшенных. В других системах фильтр применяется *после* поиска (post-filtering): система ищет top-50 ближайших, затем отбрасывает недоступные — на выходе может остаться 3–5 результатов вместо 10.
- Single binary, без внешних зависимостей (air-gapped)
- REST/HTTP API — прямая интеграция из PHP
- Apache 2.0 лицензия (closed commercial use OK)

## Варианты

| | Суть |
|---|---|
| **Qdrant** | Rust; payload filtering in ANN; single binary; REST; Apache 2.0 |
| Milvus | Go; тяжёлый (etcd + MinIO); избыточен при ≤ 50k векторов |
| Weaviate | Go; multi-tenancy, но 3+ контейнера в проде; REST есть, но основной query API — GraphQL, сложнее интеграции из PHP |
| pgvector | расширение PostgreSQL; нет фильтрации в ANN, деградация HNSW |
| LanceDB | Embedded; immaturity, нет production track record |

## Решение

**Qdrant** (Apache 2.0). Один контейнер, REST-over-HTTP, payload filtering нативен — RBAC = `Filter{ access_level <= user_role }` в теле запроса поиска.

- Контейнер `kb_qdrant`, сеть `kb_internal`, без публикации портов хоста (6.4) — по аналогии с ADR-0001/0005.
- Персистентность — `docker_volume` под `/qdrant/storage` (снапшоты коллекций через `POST /collections/{name}/snapshots`).
- Версия образа и sha256-digest фиксируются в `infra/main.tf` при реализации (паттерн ADR-0002–0005).

## Последствия

Плюс:
- Filtering не деградирует ANN (inverted index на payload)
- Без квантизации 50 k векторов (1024-d, float32) ≈ 200 MB RAM. Со scalar quantization (int8) векторы — ≈ 50 MB (+ overhead HNSW-графа сверху, оригиналы можно держать на диске)
- PHP → HTTP → `POST /collections/{name}/points/search` с фильтром в теле JSON — тривиально
- Готовый `/metrics` (Prometheus-формат) — можно подключить через Alloy в существующий стек (ADR-0002/0003); в MVP не обязательно

Минус:
- Нет ACID-транзакций между коллекциями (не критично: метаданные предполагаются в PostgreSQL — БД метаданных пока не развёрнута и не имеет своего ADR, требуется отдельное решение)
