# ADR-0003: Принять Grafana Alloy как единый агент сбора телеметрии

Статус: принят  
Deciders: AI Architect  
Дата: 2026-09-19  
Техническая история: ТЗ-ТМ-2026-014, п. 5 (FR-9), 7.9, 8.4

## Контекст

ADR-0002 закрепляет Grafana OSS как единый слой визуализации и алертинга, а в качестве data sources — Prometheus (метрики), Loki (логи), Tempo (трейсы). Остал нерешённым вопрос **слоя сбора**: кто собирает телеметрию с компонентов Платформы (vLLM, MCP-сервер, PHP, Nginx, GPU) и как передаёт её в эти бэкенды.

Требования: FR-9/7.9 — сквозной трэйс запроса (вопрос → ретривал → агент → генерация) + метрики (токены/сек, TTFT, RPS, GPU/VRAM); 8.4 — полный трэйс и логи LLM-сервера должны быть видны в инструменте трейсинга. Трейсинг — OpenTelemetry. Всё — в закрытом контуре (6.3), сегментация DMZ/Internal (6.4), без DevOps в штате (2.2).

## Драйверы

- FR-9/8.4: один сборочный слой для трейсов (OTel) + метрик + логов
- Нет DevOps в штате: минимум коллекторов, конфигов и циклов обновлений
- Закрытый контур (152-ФЗ): только self-hosted, без внешних API
- Единый декларативный конфиг — воспроизводимость (продолжение ADR-0001)

## Варианты

| | Суть |
|---|---|
| A. Раздельные коллекторы (Prometheus-scrape + promtail + OTel Collector) | Зрелые по отдельности, но 3+ демона-коллектора: 3 конфига, 3 цикла обновлений; node_exporter/cAdvisor — отдельные цели скрейпа |
| **B. Grafana Alloy — единый агент** | Один процесс (на базе OTel Collector): prometheus.scrape/remote_write + loki.source (promtail) + otelcol receiver/exporter; маршрутизация в Prometheus/Loki/Tempo |
| C. Grafana Cloud (SaaS) | Нарушает п. 6.3/152-ФЗ — **исключён** |

## Решение

**Вариант B.** Grafana Alloy — единый агент сбора: собирает метрики (Prometheus-скрейп), логи (Loki/promtail) и трейсы (OTel-receiver) с компонентов Платформы и маршрутизирует их в бэкенды ADR-0002 (Prometheus, Loki, Tempo). Alloy **не заменяет хранилища** — он только собирает и маршрутизирует (remote write / OTLP / Loki push); хранение остаётся за бэкендами.

**Развёртывание.** Контейнер `kb_alloy` в сегменте **Internal** (сеть `kb_internal`), управляется Terraform (продолжение ADR-0001), host-порты наружу не публикует: компоненты Платформы (vLLM, MCP, Nginx) отдают ему OTLP/скрейп по внутренней сети; node_exporter/cAdvisor — лёгкие контейнеры-цели скрейпа для метрик хоста и GPU/VRAM.

**Лицензия.** Grafana Alloy — **AGPL-3.0**: допустимо, т.к. сервис автономен и copyleft не распространяется на код Платформы; модификации/редистрибуция не допускаются — используем дистрибутив как есть (аналогично ADR-0002).

## Последствия

Плюс:
- Один агент вместо тройки коллекторов (Prometheus-scrape + promtail + OTel Collector) → один конфиг, один апгрейд, один health-check
- OTel-нативность: единый `otelcol`-receiver принимает трейсы/метрики от vLLM, MCP (PHP), Nginx и направляет в Tempo — закрывает сквозной трэйс FR-9
- Метрики GPU/VRAM, CPU, RAM (FR-9) — одним агентом (скрейп cAdvisor/node_exporter), без отдельных конвейеров
- Единая экосистема вендора (Grafana Labs) → согласованность конфига с бэкендами и дашбордами ADR-0002
- Self-hosted, air-gapped — соответствует п. 6.3

Минус:
- AGPL-3.0: нет редистрибуции модификаций (на код Платформы не влияет)
- Проект моложе выделенных Prometheus/promtail/OTel Collector → круче кривая обучения, меньше примеров
- Встроенного long-term-хранилища нет (только remote write/OTLP/Loki push) → Prometheus/Loki/Tempo по-прежнему нужны как бэкенды (ADR-0002)
- В MVP один агент = SPOF для сбора (HA-реплика — за пределами MVP)
