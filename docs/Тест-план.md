## 2. Качество ответов: LLM-as-a-Judge

### Набор вопросов

`testdata/questions.json` — 48 вопросов по пилотному корпусу (ТЗ, п. 4.5), тот же пул, что в нагрузочном тесте.
У каждого вопроса: категория, ожидаемый исход (ответ или отказ), ожидаемые документы-источники, гриф.

| Категория | Вопросов | Гриф | Что проверяет |
|---|---|---|---|
| По одному документу | 26 (20 RU, 6 EN) | публичный | Ответ из паспорта или руководства модели |
| Multi-hop | 10 | служебный (9), конфиденциальный (1) | Ответ из двух документов, связанных моделью изделия: «акт ремонта → паспорт или руководство этой модели» (п. 8.2) |
| История обслуживания | 6 | служебный (4), конфиденциальный (2) | Сводка по нескольким сервисным актам |
| Вне корпуса | 6 | публичный | Отказ «Нет данных в базе знаний» (FR-5) |

Вопросы составлены по названиям документов, без чтения их текста: у части вопросов ответа в документе может не быть.

### Методика

- **Прогон** — команда `testdata:judge` (`backend/app/Console/Commands/JudgeAnswers.php`). Каждый вопрос задаётся
  конвейеру RAG (`KnowledgeBaseRag`: поиск, граф, реранкер, генерация) с допуском, равным грифу вопроса.
  Входные и выходные guardrails в прогон не входят — у них свои автотесты. Из состояния агента берутся ответ,
  фрагменты, которые получила модель, и их документы.
- **Судья** — `AnswerJudge`: та же генеративная модель (ADR-0009), температура 0, с рассуждением перед вердиктом.
  Судья видит вопрос, фрагменты и ответ и оценивает только по фрагментам: сведения, которых во фрагментах нет,
  считаются неподтверждёнными, даже если они верны.
- **Метрики ответа** (судья):
  - *опора на фрагменты* (faithfulness), 1–5: 5 — каждое утверждение подтверждено фрагментами, 1 — ответ
    не следует из фрагментов;
  - *полнота* (completeness), 1–5: 5 — ответ на все части вопроса, 3 — нет ответа на одну из частей;
  - *ссылка на источник* — называет ли ответ документ, из которого взяты сведения;
  - *неподтверждённые утверждения* — перечень, для ручной проверки.
- **Метрика отказа** (судья): есть ли во фрагментах ответ хотя бы на часть вопроса. Сведения о другой модели или
  серии ответом не считаются.
- **Метрика поиска** (без модели): доля ожидаемых документов, попавших во фрагменты модели (recall источников).
- **Исход вопроса:**

| Исход | Условие | Прошёл |
|---|---|---|
| `answered` | ответ; опора ≥ 4 и полнота ≥ 4 | да |
| `answered_poorly` | ответ; опора или полнота < 4 | нет |
| `correct_refusal` | отказ на вопрос вне корпуса | да |
| `answered_out_of_corpus` | ответ на вопрос вне корпуса | нет |
| `refused_nothing_found` | отказ: ни один фрагмент не прошёл порог реранкера | нет |
| `refused_answer_not_found` | отказ: во фрагментах ответа нет — промах поиска или ответа нет в документе | нет |
| `refused_answer_in_fragments` | отказ: во фрагментах есть ответ хотя бы на часть вопроса — ошибка генерации | нет |

- **Отчёт** — `results.json` (по каждому вопросу: ответ, фрагменты, документы, вердикт и обоснование судьи)
  и `summary.json`. Каталог `testdata/reports/` в `.gitignore`: во фрагментах сервисных актов — метки ПДн.

Повторить на стенде (`testdata/` в `kb-app` не смонтирован):

```bash
docker cp testdata/questions.json kb-app:/tmp/questions.json
docker exec -u www-data kb-app php artisan testdata:judge --questions=/tmp/questions.json --out=/tmp/judge
docker cp kb-app:/tmp/judge testdata/reports/$(date +%F)-judge
```

### Ограничения метода

- **Самооценка.** Судья — та же модель, что отвечает: другой в закрытом контуре нет (ТЗ, п. 1.2). Модель может
  не замечать собственных ошибок того же рода.
- **Судья проверен выборочно.** Около 10 вердиктов сверены с фрагментами вручную. Вердикты по отказам после
  уточнения правила о другой модели совпали с ручной оценкой. Вердикты по ответам бывают мягкими: в одном
  из прогонов ответ с искажёнными номерами контактов из таблицы получил 5/5 (q15).
- **Без рассуждения судья не работает.** vLLM ограничивает вывод JSON-схемой, но описаний полей модель не видит:
  без рассуждения она заполняла схему случайными значениями. Смысл полей — в тексте задания судье,
  рассуждение включается в запросе.
- **Разброс между прогонами.** Модель ответа генерирует с температурой 0,2: исход отдельных вопросов
  (q31, q34) менялся от прогона к прогону. Итог по набору — ±1–2 вопроса.

### Что дальше

- Ссылки на источники добавлять к ответу инструмента кодом по документам фрагментов, а не просить об этом модель:
  доля ответов со ссылкой — условие п. 9.4.
- Сверить q05, q17, q18, q25 с документами: исправить вопросы без ответа в корпусе или разобрать поиск.
- Multi-hop: разрешить модели ответить на найденную часть составного вопроса; передавать реранкеру связь
  «модель — акт» для второго документа.
