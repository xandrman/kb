## Часть 1. Обработка документов

### Методика

- **Корпус** — пилотный корпус (ТЗ, п. 4.5): 100 публичных документов SNR (75 RU / 25 EN, до 52 страниц,
  1 530 страниц в обработанных) и 50 синтетических сервисных актов (40 PDF, 5 PNG, 5 JPEG).
  Состав — `testdata/registry.json` и `testdata/synthetic/manifest.json`, генерация актов —
  «Синтетические сервисные акты.md».
- **Загрузка** — командой `testdata:import`: тот же путь, что загрузка через админ-панель
  (`StoreUploadedDocument`), все 150 документов поставлены в очередь за 7 с.
- **Сбор** — раз в минуту: число документов по статусам (PostgreSQL) и загрузка GPU (`nvidia-smi`);
  по окончании — длительности этапов из `documents`: `docling_processing_time` (извлечение),
  `indexing_time` (чанкование), `graph_time` (фрагменты: маскирование ПДн, векторный индекс, граф).
  `graph_time` считается от постановки заданий фрагментов до последнего из них — в него входит ожидание
  в очереди `graph` за фрагментами других документов.
- **Один документ** — отдельный замер на документе, ближайшем к пределу ТЗ: руководство ИБП SNR серии SM
  100–500 кВА, 92 страницы, EN; загружен при пустых очередях.

Сырые данные — `testdata/reports/2026-09-24-ingest/` (каталог в `.gitignore`).

### Находки

1. **Чанкование блокируется конвертацией.** С движком RQ синхронный `/v1/chunk/hybrid/file` ставит задачу
   `chunk` в ту же очередь, что `convert`, и её разбирает тот же единственный `rq-worker`. Пока в очереди
   150 конвертаций, чанкование первого документа не укладывается в таймаут клиента 60 с. `kb-worker` — один
   процесс на всю очередь `documents`: каждый таймаут занимает его на минуту, опрос остальных документов стоит.
   Каждый повтор оставляет в очереди docling ещё одну задачу `chunk`. В прогоне до 19:26 ни один документ
   не прошёл чанкование, хотя 20 уже были извлечены; чанкование пошло, когда очередь конвертации разошлась.
   *Рекомендация:* асинхронное чанкование (`…/async` + опрос, как для конвертации) или конвертация с
   чанкованием одной задачей docling; несколько процессов `kb-worker`.
2. **PDF-сканы не распознаются.** `ChooseDoclingRoute` отправляет любой PDF по стандартному маршруту без OCR;
   проверка текстового слоя из ADR-0012 не реализована. 5 из 100 публичных документов (132 страницы) не попали
   в базу знаний.
   *Рекомендация:* реализовать проверку текстового слоя и отправлять PDF без текста по VLM-маршруту.
3. **Детектор ПДн может не завершить ответ.** На одном фрагменте `service-act-025.pdf` модель генерировала
   ≈ 9 000 токенов за 60 с (150 токенов/с) и не закончила; все 5 попыток оборвались таймаутом клиента.
   Четыре из пяти попыток шли без других запросов к vLLM — дело не в нагрузке. У запроса нет `max_tokens`,
   `temperature = 0` делает повторы одинаковыми.
   *Рекомендация:* `max_tokens` для детектора ПДн (≈ 1 024) и извлечения графа (2 048–4 096), штраф за повторы,
   таймаут клиента ≈ 120 с, согласованный с лимитом.
4. **`graph:merge-synonyms` падает молча.** При лимите памяти PHP по умолчанию (256 МБ) на графе 142 документов
   команда завершается с кодом 255 без сообщения; с 1 ГБ — проходит за 14 минут. Слияние не запускается после
   обработки автоматически.
   *Рекомендация:* обрабатывать сущности порциями или поднять лимит для команды; запускать слияние после
   обработки пакета документов.
5. **Генеративная модель загружена наполовину.** Восемь воркеров графа дают не более 8 одновременных запросов
   при 16 слотах vLLM; очереди в vLLM не было, GPU 0–1 загружены в среднем на 65 %. При массовой загрузке
   документы ждут в очереди `graph` до 30+ минут.
   *Рекомендация:* поднять `graph_workers` до 12–14, оставив слоты для ответов пользователям: при 16 пользователях
   ответы на вопросы занимали не более 4 слотов (часть 2).

## Часть 2. Ответы на вопросы

### Методика

- **Что вызывается** — MCP-инструмент `search` (FR-5) методом `tools/call` по HTTP, как его вызывает система диалогов:
  из сети `kb-internal` на `http://kb-nginx/mcp`, ответ потоком SSE. Генератор нагрузки — скрипт на Python
  в контейнере той же сети (`testdata/reports/2026-09-25-mcp/loadtest.py`).
- **Пользователь** — `kb-admin` с допуском «конфиденциально», токен Keycloak с `aud=kb-app`. Токен получался через
  временный клиент Keycloak с password grant; после теста клиент удалён.
- **Вопросы** — пул из 48 вопросов (`testdata/questions.json`): 26 по одному документу (20 RU, 6 EN),
  10 multi-hop «акт → паспорт/руководство», 6 по истории обслуживания (сводка по нескольким актам),
  6 вне корпуса. Каждый виртуальный пользователь задаёт их по кругу в своём случайном порядке.
- **Профиль нагрузки** — 1, 5, 10 и 16 одновременных пользователей, по 5 минут на уровень, пауза 30 с между уровнями.
  Между вопросами пользователь «читает ответ» 15–25 с. Пауза нужна и потому, что MCP ограничивает одного
  пользователя 60 запросами в минуту, а все виртуальные пользователи работают под одной учётной записью.
- **Замеры на клиенте:**
  - *TTFT* — от отправки запроса до уведомления «Формирую ответ…», которое инструмент шлёт в момент начала
    генерации ответа. Для отказа без генерации («Нет данных в базе знаний») TTFT равен полному ответу;
  - *полный ответ* — до результата `tools/call`;
  - *RPS* — успешные ответы за время уровня.
- **Замеры на сервере** — по окну каждого уровня из Prometheus: спаны `mcp.ttft` и `mcp.tool search`
  (`traces_spanmetrics_latency`, P95 оценён по корзинам гистограммы) и метрики `kb-vllm-generate`.

В TTFT и полный ответ не входит ответ модели чата: пользователь видит текст, который модель чата пишет
по результату инструмента (ADR-0031). Система диалогов в замер не включена.

### Наблюдения

- **Ошибки 500 (4 из 428, 0,9 %)** — на 10 и 16 пользователях. Причина — гонка при синхронизации ролей из токена:
  одновременные запросы одного пользователя вставляли одну и ту же запись в `model_has_roles`
  (`duplicate key … model_has_roles_pkey`). После теста исправлено в `SyncKeycloakRoles`; в повторном замере
  ошибок нет (0 из 431).
- **Доля отказов не зависит от нагрузки**: 50 % на 1 пользователе, 51 % на 16. По категориям: вне корпуса — 100 %
  (ожидаемо), multi-hop — 100 %, по одному документу — 30 %, история обслуживания — 0 %. Составной вопрос
  «что ремонтировали по акту + характеристика из паспорта» получает отказ целиком, хотя первая часть отвечается
  отдельно: обход графа от акта уходит в сущности ремонта, а не в модель устройства. Вопросы пула составлены
  без чтения документов, часть отказов по одному документу может быть верной — качество ответов оценивается
  функциональным тестом (LLM-as-a-Judge), не этим отчётом. Для критерия пилота «≥ 90 % ответов со ссылками»
  (п. 9.4) это риск.

  Разбор 25.09.2026 нашёл у multi-hop две причины. Первая — акт не находился по номеру: номера не было в индексе
  (см. «Качество обработки»), а эмбеддинги почти не различают номера похожих актов. Вторая — от акта обход не доходил
  до документа модели: модель изделия связана больше чем с 30 сущностями, и обход обходит её как хаб
  (`GRAPH_MAX_DEGREE`). Исправлено: чанки с номером акта или кодом модели из вопроса ищутся точным совпадением,
  второй шаг идёт через модель изделия к ближайшим к вопросу чанкам других документов о ней. После исправления
  ответ дан на 6 из 10 multi-hop вопросов — оценка качества в «Тест-план.md»; в повторном замере под нагрузкой
  отказов на multi-hop 51 %.
- **Таймаут nginx для `/mcp` — 60 с** (`fastcgi_read_timeout`). Максимальный ответ в тестах — 9,8 с, запас есть;
