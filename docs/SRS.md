## 1. Общие положения

1.1. Настоящее техническое задание (ТЗ) определяет требования к проектированию и реализации MVP (минимально жизнеспособного продукта) производственного конвейера полного цикла извлечения знаний из неструктурированных документов в закрытом контуре (далее — Платформа).

1.2. Платформа должна работать **полностью автономно** (on-premise / air-gapped) без обращения к внешним API (в том числе облачным LLM-провайдерам).

1.3. Полный цикл обработки:
1. **Вход** — загрузка неструктурированных документов (сканы, чертежи, PDF).
2. **Обработка** — извлечение текста, чанкование, построение графа знаний, индексация векторов.
3. **Запрос** — пользователь задаёт вопрос в **системе диалогов с LLM** → MCP-инструмент (GraphRAG) → генерация ответа локальной LLM.

1.4. Ключевые проблемы, которые Платформа обязана решить: «галлюцинации» и «потеря контекста» — через внедрение **GraphRAG** (нейро-символический подход), и защита корпоративных данных — через **Security-by-Design** (разграничение доступа к данным на уровне чанков/узлов графа).

### Глоссарий

| Термин | Значение |
|---|---|
| GraphRAG | Генерация, дополненная поиском, с использованием графа знаний (комбинация векторного и графового поиска) |
| Чанк | Семантически завершённый фрагмент документа, единица индексации и разграничения доступа |
| Узел / ребро графа | Сущность (продукт, компонент, операция и т.п.) и отношение между сущностями в графе знаний |
| Guardrails | Контрольные точки фильтрации входных и выходных данных (PII, prompt injection и др.) |
| RBAC | Модель разграничения доступа по ролям |
| Control Plane / Data Plane | Слой управления (агенты, оркестрация) / слой данных (БД, модели, инференс) |
| TTFT | Время до первого токена (Time To First Token) |
| MCP | Model Context Protocol — протокол подключения внешних инструментов (tools) к LLM-агентам |
| Система диалогов с LLM | Self-hosted веб-интерфейс для взаимодействия с LLM в виде чатов (user channel) |
| Keycloak | Open-source Identity & Access Management (IAM); источник аутентификации пользователей |

## 2. Бизнес-контекст и проблематика

2.1. **О Заказчике.** ООО «TechnoMart» — ритейлер бытовой техники и электроники в топ-5 страны: сеть из 150 офлайн-магазинов, e-commerce (сайт + мобильное приложение), ~2 млн активных пользователей в месяц (MAU), ассортимент более 50 000 SKU.

2.2. **Текущий технический ландшафт.** E-commerce — монолит на PHP (1С-Битрикс) + MySQL; учёт, каталог и заказы — 1С; поведенческая аналитика — Google Analytics. Аутентификация — **Keycloak**. В компании развёрнут **self-hosted веб-интерфейс для взаимодействия с LLM в виде чатов**, используемый сотрудниками. Команда Заказчика располагает сильной группой PHP-разработчиков; специалистов ML/Data Engineering в штате нет.

2.3. **Проблема.** Знания о продукции (руководства пользователя, сервисные и ремонтные инструкции, условия гарантии, контракты с поставщиками, ГОСТы, чертежи, отсканированные акты и паспорта оборудования) хранятся в неструктурированных файлах и разрозненны по отделам. Следствия:
- сервисные инженеры, служба поддержки и продавцы тратят значительное время на поиск информации;
- ошибки в гарантийных разбирательствах и консультациях из-за фрагментарного знания;
- использование внешних (облачных) LLM **недопустимо**: сервисные акты содержат персональные данные клиентов (ФИО, телефоны, адреса), коммерческие документы содержат конфиденциальные условия поставок. Данные не должны покидать периметр (соответствие 152-ФЗ).

2.4. **Бизнес-цели.**
- Сократить среднее время ответа поддержки/сервиса на запросы по документации продукции;
- Исключить необоснованные ответы: ответ формируется **исключительно на основе документов, загруженных в базу знаний**, при отсутствии соответствующих документов — явный отказ;
- Создать единую базу знаний по всей линейке техники с связями «продукт — компонент — сервисная операция — документ».

- промышленная миграция данных сверх пилотного корпуса.

## 4. Входные данные

4.1. **Типы документов:** PDF, PNG, JPEG (руководства, инструкции, контракты, сервисные акты, паспорта оборудования, таблицы внутри документов).

4.2. **Метаданные документа:** SKU, тип документа, гриф доступа (общедоступный / служебный / конфиденциальный), отдел-владелец, дата.

4.3. **Пилотный корпус:** 125–500 документов, до 50 страниц на документ. Язык — русский, английский.

4.4. **Персональные данные:** в сервисных актах могут содержаться ФИО, телефоны, адреса клиентов — обязательная фильтрация/маскирование до индексации (см. FR-8).

4.5. **Состав пилотного корпуса.** Реальные сервисные документы Заказчика содержат ПДн и являются конфиденциальными, поэтому пилотный корпус формируется из следующих компонентов:

| № | Компонент | Объём | Назначение | Источник |
|---|---|---|---|---|
| 1 | **Синтетические сервисные документы:** акты приёма в ремонт, акты выполненных ремонтных работ, гарантийные талоны, технические паспорта оборудования | 50 док. | Ядро базы знаний: сервисный домен; ПДн для сценариев PII-guardrails и RBAC | Генерация из форм-шаблонов локальной LLM (данные синтетические, структура — по формам Заказчика) |
| 2 | Публичные руководства и сервисные инструкции по технике (реальные PDF) | ~100 док. | Демо-сценарий «вопрос по документации техники» | Официальные сайты производителей (открытое распространение) |

4.6. **Валидация OCR-этапа.** Для проверки качества распознавания рукописных полей и технических чертежей допускается использование открытых русскоязычных OCR-наборов (рукописный текст, текст технических чертежей) как вспомогательного тестового сета.

## 5. Функциональные требования

Приоритеты: **M** — обязательно к сдаче (MVP), **S** — желательно.

| № | Требование | Приоритет |
|---|---|---|
| FR-1 | **Админ-панель:** веб-интерфейс с аутентификацией и авторизацией через Keycloak (роль «администратор»); загрузка документов; асинхронная обработка с видимым статусом (очередь) и повторной обработкой; список документов и статусы обработки; статистика корпуса | M |
| FR-2 | **Извлечение текста:** в т.ч. OCR сканов; распознавание таблиц; сохранение структуры (заголовки, страницы, таблицы) | M |
| FR-3 | **Чанкование и индексация:** семантическое чанкование с метаданными (документ, страница, SKU, гриф доступа); векторный индекс чанков | M |
| FR-4 | **Граф знаний:** извлечение сущностей и связей локальной LLM; дедупликация сущностей (слитие синонимов); привязка узлов к документам и чанкам | M |
| FR-5 | **Запрос:** пользователь задаёт вопрос в **системе диалогов с LLM** → вызов **MCP-инструмента (GraphRAG)** → гибридный поиск (векторный + графовый) → ответ **со ссылками на источники** (чанки/узлы); при отсутствии источников в корпусе — отказ «нет данных в базе знаний», генерация ответа из весов модели без опоры на документы запрещена | M |
| FR-6 | **Streaming** генерации ответа пользователю | S |
| FR-7 | **RBAC:** аутентификация пользователей — токен Keycloak, получаемый MCP-сервером от системы диалогов; роли пользователей; права доступа к чанкам/узлам графа; пользователь без полномочий **не получает** ответ, основанный на ограниченном документе, в том числе опосредованно (через связанные узлы) | M |
| FR-8 | **Guardrails:** входные (фильтрация PII, защита от prompt injection) и выходные (утечка PII, утечка контекста) — как **отдельные контрольные точки** с обоснованием невозможности объединения в единый фильтр; логирование заблокированных запросов | M |
| FR-9 | **Observability:** сквозной трэйс запроса (вопрос → ретривал → агент → генерация); метрики: токены/сек, latency (TTFT/полный ответ), RPS, утилизация GPU/VRAM | M |

## 6. Нефункциональные требования

### 6.1. Производительность (на эталонном оборудовании, п. 7.2)

| Метрика | Требование |
|---|---|
| TTFT (P95) | ≤ 5 с |
| Полный ответ (P95) | ≤ 30 с |
| Одновременные пользователи | ≥ 10 |
| Нагрузочный отчёт | измеренные RPS и latency — обязательный артефакт |

Допускается осознанная деградация latency в пользу целостности закрытого контура; деградация фиксируется в отчёте.

### 6.2. Обработка документов

- Один документ (до 100 страниц) — не более 30 минут;
- Параллельная обработка ≥ 2 документов;

### 6.3. Технологический суверенитет

- Отсутствие обращений к внешним API и облачным моделям (air-gapped);
- Все компоненты — self-hosted; модели — open source с лицензиями, совместимыми с закрытым коммерческим использованием;
- Поддержка русского языка LLM и embedding-модели.

### 6.4. Безопасность

- Соответствие 152-ФЗ: ПДн и коммерческая тайна не покидают периметр;
- Шифрование каналов между сервисами (TLS);
- Хранение секретов в выделенном сервисе (Vault) с мастер-ключом, порядок владения ключом — в документации;
- Аудит-лог доступа пользователей к ограниченным документам;
- Доступ к админ-панели — **только для пользователей с ролью «администратор»**;
- Сегментация сети: DMZ / Internal.

### 6.5. Масштабируемость и изменяемость

- Разделение Control Plane (агенты, оркестрация) и Data Plane (БД, модели, инференс);
- **Шов расширения:** добавление нового типа узла графа или нового инструмента без переделки конвейера;
- Горизонтальное масштабирование Data Plane при росте нагрузки.

## 7. Требования к архитектуре и платформе

7.1. **Развёртывание:** on-premise в закрытом контуре.

7.2. **Эталонное оборудование:** сервер на базе EPYC + **4× RTX 3090 (24 GB VRAM)** (итоговый бюджет VRAM — 96 GB с учётом ОС и вспомогательных процессов). Комплект моделей и схема квантования обязаны укладываться в данный бюджет; расчёт VRAM/CPU/RAM (Capacity Planning) — обязательный раздел документации.

7.3. **LLM Serving:** высокопроизводительный локальный сервер инференса (vLLM, SGLang, TGI или эквивалент) с **квантованием моделей** под consumer VRAM и оптимизацией **KV-cache**.

7.4. **Модели:** pre-trained open source с поддержкой русского: генеративная LLM, embedding-модель, reranker. Обучение моделей не допускается.

7.5. **Хранилища (self-hosted):** векторная БД, графовая БД, реляционная БД (метаданные, пользователи, сессии, аудит), кэш/очереди.

7.6. **Язык реализации:** прикладной слой Платформы (MCP-сервер, админ-панель, RAG-конвейер) — **PHP 8.x**.

7.7. **LLM-serving:** выделенный микросервис (vLLM/SGLang/TGI); взаимодействие с ним — через HTTP.

7.8. **Интеграция:** Платформа предоставляется пользователям в виде **MCP-сервера**, интегрируемого в **существующую систему диалогов с LLM**. MCP-сервер получает токен пользователя от **Keycloak**, определяет роль и **применяет RBAC на уровне чанков/узлов графа** перед формированием ответа.

7.9. **Observability:** распределённый трейсинг + метрики и дашборды.

7.10. **Документация (обязательная часть поставки):**
- полный набор **ADR** с trade-off анализом выбранного стека (актуальность 2026, РФ), лицензиями и физическим развёртыванием;
- **C4 Level 1** — интеграция Платформы в ландшафт Заказчика;
- **C4 Level 2** — контейнерная/микросервисная архитектура;
- **C4 Level 3** — внутреннее устройство MCP-сервера;
- **Deployment Diagram** — GPU-ресурсы, балансировка, сегментация сети (DMZ/Internal), Vault, Keycloak;
- **Sequence Diagram** — флоу запроса: User (система диалогов с LLM) → Keycloak (token) → MCP-сервер (Input Guardrails → RBAC → RAG → Rerank) → LLM (stream) → Output Guardrails → Response;
- **ER Diagram** — векторы, чанки, история сессий, логи, права доступа (RBAC);
- **Capacity Planning** — расчёт VRAM/CPU/RAM под эталонное оборудование;
- пояснительная записка к деплой-схеме.

## 8. Критерии приёмки (MVP)

Приёмке подлежит система, для которой одновременно верны:

1. Сквозной конвейер работает в закрытом контуре без доступа в интернет.
2. Демонстрируется ответ на **multi-hop вопрос** на основе графа со ссылками на источники из корпуса; при отсутствии источников — отказ.
3. **Проверка RBAC:** второй пользователь (без полномочий) не получает ответ, основанный на ограниченном документе (в т.ч. опосредованно через граф).
4. В инструменте трейсинга виден полный трэйс запроса; представлены логи LLM-сервера.
5. Предоставлен нагрузочный отчёт: измеренные RPS и latency на эталонном оборудовании.
6. Предоставлен полный пакет документации (п. 7.10) и тест-план; качество ответов измерено методом LLM-as-a-Judge на пилотном корпусе, метрики включены в отчёт.
7. Предоставлено видео-демо объёмом 5–7 минут с демонстрацией работы «под капотом».
8. Код размещён в git-монорепо: `/infra` (инфраструктура), `/backend` (агенты и API), `/docs` (документация).

## 9. План пилотного внедрения

9.1. **Способ внедрения.** Платформа вводится в пилотную эксплуатацию путём подключения разработанного Исполнителем MCP-сервера (GraphRAG tool) к существующей self-hosted системе диалогов с LLM Заказчика. Отдельный пользовательский интерфейс не создаётся: сотрудники работают через штатный чат; аутентификация и RBAC — по токену Keycloak (п. 7.8).

9.2. **Аудитория пилота.** Пилотными пользователями выступают сотрудники Заказчика (сервисные инженеры, служба поддержки, продавцы и иные отделы — по усмотрению Заказчика). Состав ролей и доступ к ограниченным документам определяются Заказчиком средствами Keycloak и применяются MCP-сервером согласно FR-7.

9.3. **Загрузка корпуса.** Пилотный корпус (п. 4.5, до 500 документов) загружается Заказчиком через админ-панель (FR-1) с обязательным заполнением метаданных (SKU, тип документа, гриф доступа, отдел-владелец) для корректной работы RBAC и guardrails.

9.4. **Критерии успеха пилота.** Пилот считается успешным при выполнении критериев приёмки (п. 8), в том числе:

- не менее 90 % запросов из пилотного набора Q&A-сценариев, согласованного Сторонами до запуска пилота, завершаются ответом со ссылками на источники, а не отказом «нет данных в базе знаний»;
- отсутствие инцидентов утечки ПДн и коммерческой тайны, подтверждаемое аудит-логом (FR-8, п. 6.4);
- подтверждение RBAC: пользователь без полномочий не получает контент ограниченных документов ни напрямую, ни опосредованно через граф;
- значения TTFT и полного ответа в пределах п. 6.1 при ≤ 10 одновременных пользователях.

9.5. **Завершение пилота.** По итогам пилота Сторонами принимается решение о масштабировании; план масштабирования входит в состав поставки (п. 10, артефакт 9).
